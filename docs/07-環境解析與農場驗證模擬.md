# Rez 環境解析與農場驗證端到端模擬演練

本文檔提供端到端（End-to-End）實戰模擬步驟，涵蓋工作站解析、Memcached 快取命中測試、TD 本機除錯隔離（情境 B）以及跨平台 Context 算圖派送驗證。

---

## 模擬場景一：工作站多 DCC 解析與 Memcached 快取驗證

### 1. 首次解析（冷啟動 / Cold Resolve）
在 Windows 藝術家工作站上執行複合環境解析請求：

```powershell
# 請求包含 Houdini 20.5.278、Maya 2024 與 Nuke 15.1.1 的環境
rez-env houdini-20.5.278 maya-2024 nuke-15.1.1 -- python -c "import os; print('HFS:', os.environ.get('HFS')); print('MAYA_LOCATION:', os.environ.get('MAYA_LOCATION')); print('NUKE_LOCATION:', os.environ.get('NUKE_LOCATION'))"
```

* **系統內部行為**：
  1. Rez 掃描 `packages_path`，在中央 NAS（`X:/rez-system/packages`）讀取 `houdini`、`maya` 與 `nuke` 的 `package.py`。
  2. 計算相依性無衝突後，將解析結果序列化。
  3. 若 `resolve_caching = True`，Rez 會將解析結果寫入 Memcached 伺服器 `192.168.0.221:11211`。
* **輸出結果**：
  ```text
  HFS: C:/Program Files/Side Effects Software/Houdini 20.5.278
  MAYA_LOCATION: C:/Program Files/Autodesk/Maya2024
  NUKE_LOCATION: C:/Program Files/Nuke15.1v1
  ```

> [!NOTE]
> **多 DCC 合併環境僅供驗證**
>
> 此處將三個 DCC 放入同一環境，只為驗證 Wrapper 的環境變數。Nuke 沒有獨立的 `bin/`，整個安裝根目錄（含 Nuke 自帶的 `python.exe` 與大量 DLL）都會被加入 `PATH`，因此在合併環境中執行 `python`，實際執行的可能是 DCC 內建的直譯器而非系統 Python。正式啟動軟體時，每次只請求單一 DCC 及其外掛。

### 2. 二次解析（熱快取 / Hot Resolve Hit）
在同一台電腦或其他任一工作站再次執行相同請求：

```powershell
rez-env houdini-20.5.278 maya-2024 nuke-15.1.1 -- echo "Environment Resolved"
```

* **系統內部行為**：
  Rez 直接比對請求特徵碼，命中 Memcached 快取，耗時由實體磁碟遍歷降至毫秒級，且大幅減少對中央 NAS 的 stat / read I/O。
* **檢查 Memcached 統計數據**：
  ```powershell
  rez-memcache --stats
  ```
  可觀察到 `cmd_get` 與 `get_hits` 次數增加，代表解析快取運作正常。

### 3. 切換至新版專案環境

同一套中央套件庫可並存另一組 DCC 版本。新版專案以完整版本請求建立獨立解析結果：

```powershell
rez-env houdini-22.0.368 maya-2027 nuke-17.1.1 -- python -c "import os; print('HFS:', os.environ.get('HFS')); print('MAYA_LOCATION:', os.environ.get('MAYA_LOCATION')); print('NUKE_LOCATION:', os.environ.get('NUKE_LOCATION'))"
```

預期輸出：

```text
HFS: C:/Program Files/Side Effects Software/Houdini 22.0.368
MAYA_LOCATION: C:/Program Files/Autodesk/Maya2027
NUKE_LOCATION: C:/Program Files/Nuke17.1v1
```

舊版與新版 Wrapper 不會互相覆寫；每組精確請求會產生各自的解析結果與快取項目。

新版 DCC 必須搭配發布支援該版本的外掛套件。例如 `htoa-6.3.3.0` 的 variants 只宣告了 `houdini-20.5.278`，`maya_usd-0.28.0` 只宣告了 `maya-2024`，因此 `rez-env houdini-22.0.368 htoa-6.3.3.0` 會解析衝突而失敗。這是預期中的 ABI 保護行為：新版專案需另行發布對應新版 DCC 的 HtoA／Maya-USD 版本，外掛不可跨 DCC 版本共用。

## 模擬場景二：Pipeline TD 本機獨立測試（情境 B 覆寫驗證）

當 TD 需要為工作室自研工具 `studio_pipeline` 開發新功能時，驗證不會干擾全公司的測試流程：

### 1. 建立本機套件
TD 先確認自己的帳號已設定 `STUDIO_REZ_DEV=1`，再於 `%USERPROFILE%\rez-client\packages\studio_pipeline\1.2.1\package.py` 撰寫修正。一般藝術家帳號不啟用此變數，因此不會搜尋本機開發庫：

```python
name = "studio_pipeline"
# 注意：Rez 版本排序中，若給定 studio_pipeline-1.2.1-beta，
# 依 Rez 規則其版本序位高於 1.2.1（因為額外 token 被視為更大）。
# 若要嚴格測試覆寫相同版本，建議版本號設為與中央庫一致的 1.2.0 或明確指定 1.2.1
version = "1.2.1"

def commands():
    env.STUDIO_PIPELINE_MODE = "DEV_LOCAL"
```

### 2. 驗證情境 B 優先載入機制
TD 在本機執行：

```powershell
rez-env studio_pipeline-1.2.1 -- python -c "import os; print(os.environ.get('STUDIO_PIPELINE_MODE'))"
# 輸出: DEV_LOCAL
```

> [!CAUTION]
> **TD 本機測試真正的農場風險**
>
> 其他美術帳號未設定 `STUDIO_REZ_DEV`，其 `packages_path` 不包含 `~/rez-client/packages`，因此 TD 本機開發不會污染其他藝術家。
> **真正的高風險情境是 TD 自己提交算圖任務**：
> 如果 TD 在本機依賴了僅存在於自己本機庫的 `studio_pipeline-1.2.1`，當送交農場時，農場固定帶有 `--no-local` 參數，農場節點將完全找不到該版本而導致任務直接噴錯。因此 TD 提交任務前，必須確認該套件已由 `rez-release` 正式推送到中央庫。

## 模擬場景三：凍結 Context 檔案與 Linux 農場派送

模擬藝術家在 Windows 電腦送出 Houdini 算圖任務，由 Linux 農場節點接手運算。

### 1. 工作站端：提交套件請求清單與時間戳
當藝術家在 Windows 提交任務時，提交器（Submitter）抓取當前工作環境的完整請求與時間鎖，記錄至算圖任務元數據：

```json
{
  "packages": ["houdini-20.5.278", "htoa-6.3.3.0", "studio_pipeline-1.2.0"],
  "timestamp": 1790000000,
  "scene_file": "X:/projects/prj_demo/shots/sh010/fx.hip"
}
```

`timestamp` 是提交器在**提交當下**記錄的 Unix 時間戳（例如 Python 的 `int(time.time())`），上例的 `1790000000` 僅為示意值。農場端以它作為 `rez-env --time` 的參數，排除提交之後才發布的套件，讓農場解析到與提交當下相同的版本。若照抄文件中的固定數字，該時間點之後發布的所有套件都會被排除。

### 2. 派遣器 / 農場適配器：路徑映射與平台專屬 Context 生成
在任務派送至 Linux 農場前，農場適配器（Farm Adapter，如 Deadline Path Mapping）：
1. 將場景路徑自 `X:/projects/...` 轉換為 `/mnt/x/projects/...`。
2. 呼叫目標平台（Linux）生成對應的 `.rxt` Context 檔案：

```bash
# 在 Linux 農場節點（或 Linux 派遣調度機）上烘焙 Context
# 工作室約定（本 repo 未附提交器／適配器實作）：
# 提交器將 Unix epoch 秒數寫入任務元數據的 "timestamp" 欄位，農場適配器讀出後設定為 SUBMIT_EPOCH
rez-env houdini-20.5.278 htoa-6.3.3.0 studio_pipeline-1.2.0 \
    --time "$SUBMIT_EPOCH" \
    --no-local \
    -o /mnt/x/jobs/1024/linux_env.rxt
```

### 3. 農場節點執行：載入專屬 Context 並啟動算圖

```bash
# 透過 -i (input) 參數載入環境，秒級重現 Linux 專屬的 Variant
rez-env -i /mnt/x/jobs/1024/linux_env.rxt -- hython /mnt/x/jobs/1024/render_script.py
```

### 4. 檢視 Context 內容
TD 若需除錯該次算圖的具體套件組合，可使用 `rez-context` 指令：

```bash
rez-context /mnt/x/jobs/1024/linux_env.rxt
```

## 四、常見異常排查指南

| 異常現象 | 可能原因 | 排除步驟 |
| :--- | :--- | :--- |
| `找不到指定的軟體安裝路徑` | 該機台未在官方預設路徑安裝 DCC | 檢查該台機器的 `C:\Program Files` 或 `/opt`，確認安裝版本是否與請求相符。 |
| `Memcached 連線逾時` | 網路不通或 11211 連接埠被防火牆阻擋 | 測試 `Test-NetConnection 192.168.0.221 -Port 11211`；Rez 具備降級機制，快取失效時會自動回退為檔案系統解析。 |
| `Linux 農場抓到 Windows DLL` | 誤將 Windows 產生的 `.rxt` 直接拿到 Linux 載入 | `.rxt` 儲存的是具體 Variant handle，無法跨平台混用。請改由目標平台解析專屬 `.rxt`。 |
| `rez-env` 出現 `PermissionError: ... .sys` 並中止 | 快取目錄存在，但實際執行 `rez-env` 的帳號沒有寫入權限（Rez 需在其中建立 `.sys/`） | Windows：以 `setup_client.ps1 -FarmNode -WorkerAccount <Worker 身分>` 重新授權 `C:\rez-cache`；Linux：確認 systemd `CacheDirectory=` 的擁有者與實際執行任務的帳號一致，或以 `install -d -o <帳號>` 重建。緊急時可先以 `rez-env --no-pkg-cache` 略過快取。 |
| `Local Cache 未發生複製` | 1. 在工作站測試：工作站依設計不啟用快取（`cache_packages_path = None`），屬預期行為<br>2. 農場節點的 `STUDIO_FARM_NODE=1` 未進入 Worker 行程環境<br>3. 套件未宣告 `cachable = True`<br>4. 快取為非同步複製，尚未完成 | 1. 快取測試請在農場節點進行，勿為此在工作站設定 `STUDIO_FARM_NODE=1`。<br>2. 在 Worker 的執行環境執行 `rez-config cache_packages_path`，應為 `C:/rez-cache` 或 `/var/cache/rez`；若為 `None`，Windows 請重啟 Deadline Worker 服務，Linux 請檢查 systemd override 並執行 `systemctl daemon-reload` 後重啟服務。<br>3. 檢查 `package.py` 是否宣告 `cachable = True`；`relocatable = True` 確保複製後的 payload 可正常運作，但不影響是否被快取。Wrapper 套件不應快取。<br>4. 以 `rez-env ... --pkg-cache-mode sync` 重新解析，或用 `rez-pkg-cache --logs` 查看複製紀錄。 |
